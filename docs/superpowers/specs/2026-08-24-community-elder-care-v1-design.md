# 社区独居老人照料系统 v1 设计规格

- 日期：2026-08-24
- 状态：书面规格已确认，可进入实施计划
- 项目类型：个人参赛演示项目
- 团队能力：1 人 + Codex 协作开发
- 计划周期：10 周
- 技术形态：Flutter Android App + Vue Web + ASP.NET Core + SQLite + ESP32/设备模拟器

## 1. 摘要

本项目面向社区内 75 岁及以上、基本能够自理，但存在慢性病、跌倒风险或社会支持薄弱情况的独居老人。它不是单纯的老人端 App，也不是以传感器数量为卖点的硬件平台，而是一套社区照料协同系统。

系统围绕一条可以完整演示、可以追责、可以回放的照料闭环展开：

> 发现异常 → 联系确认 → 分级派单 → 电话/上门/送医 → 记录结果 → 后续回访 → 关单

参赛类别以“智慧社区”为主，“智慧医疗”为协同能力。健康相关功能只做提醒、记录、风险提示和转介，不诊断疾病、不调整用药，也不代替医生、社区工作人员、家属或 120。

v1 使用 15～25 份完全虚构的老人档案，默认种子数据为 20 份。全部短信、电话、上门和送医过程均为演示模拟，并在界面中清楚标记。

## 2. 网上调研结论

### 2.1 背景依据

国家统计局公布的 2025 年数据表明，全国 60 周岁及以上人口为 32338 万人，占总人口 23.0%；其中 65 周岁及以上人口为 22365 万人，占 15.9% [S1]。这说明社区居家养老服务面对的是持续扩大的实际人群，而不是少数特殊案例。

民政部等十部门发布的探访关爱指导意见明确把独居、空巢、留守、失能等老人纳入特殊困难老人范围，要求通过上门、电话视频和远程监测了解情况，并开展需求转介和必要救援；文件提出到 2025 年底特殊困难老年人月探访率达到 100% [S2]。因此，社区真正需要的不只是一个报警按钮，而是档案、探访、事件、转介和回访能够衔接的工作闭环。

世界卫生组织指出，60 岁以上人群承受最多的致命跌倒，跌倒风险会随年龄上升；环境不安全、行动能力下降、用药影响等都是相关风险因素 [S3]。这支持系统提供风险发现、异常确认和防跌倒回访，但不支持把普通传感器包装成能够准确判断跌倒的医疗设备。

世界卫生组织 2025 年社会联结报告指出，社会隔离可能影响多达三分之一的老年人；独居、慢性病、社区资源薄弱等都可能加重孤独或隔离 [S4]。陪伴聊天可以作为接触入口，但技术不能替代真实的人际关系和线下服务。

中国人民大学基于专项调查的研究显示，2022 年 60 岁及以上人群互联网使用比例为 54.5%，数字鸿沟、网络安全风险和群体内部差异仍然存在 [S5]。因此，老人端必须采用少步骤、大字号、明确反馈的设计，同时保留电话、上门和实体按钮等非纯 App 路径。

国务院有关实施方案要求传统服务方式与智能化服务创新并行 [S7]。国家卫生健康委员会的老年人健康管理技术规范覆盖生活方式、患病和用药情况询问以及健康指导 [S8]。这两项依据共同支持“软件协助记录和提醒、线下人员负责服务和医疗判断”的边界。

《个人信息保护法》把医疗健康和行踪轨迹列为敏感个人信息，要求具有特定目的、充分必要性并采取严格保护措施 [S6]。参赛版因此坚持合成数据、最小权限、字段级授权和审计留痕。

### 2.2 痛点与软件可帮助范围

| 现实痛点 | 软件能够提供的帮助 | 软件不能解决或不能承诺的部分 |
|---|---|---|
| 老人跌倒、突发不适后不能及时被发现 | 平安签到、主动求助、设备信号、漏签规则和联系升级 | 不能保证发现所有事故，不能保证救援时效 |
| 社区档案和探访记录分散、更新不及时 | 统一档案、探访计划、任务提醒、结果回填和逾期看板 | 不能代替社区入户核实，也不能保证录入信息真实 |
| 家属、社区、志愿者之间信息断裂 | 事件负责人、分级通知、工单、状态流转和审计 | 不能凭空增加服务人员或线下资源 |
| 慢性病提醒和复诊安排容易遗漏 | 用药提醒、复诊提醒、完成记录和转介建议 | 不能诊断、开处方、改药或判断病情稳定 |
| 老人孤独、缺少稳定联系 | AI 陪聊、活动提醒、需求识别和人工关怀任务 | AI 不能替代亲友、社工或心理专业服务 |
| 老人不会使用复杂智能产品 | 大字、高对比、语音播报、单页单主操作和实体按钮 | 不能假定所有老人拥有或愿意使用智能手机 |
| 设备存在误报、掉线和重复上报 | 信号去重、待确认流程、离线提示和设备诊断 | 不能把单一设备信号直接当作事故事实 |
| 健康和家庭信息容易被过度共享 | 明确授权、字段级可见、撤回授权和审计 | 参赛版不能宣称已满足真实运营的全部合规要求 |

### 2.3 方案选择

评估过三种方向：

1. **老人超级 App**：功能直观，但把主要操作压力留给老人，无法解决社区协同和线下闭环。
2. **设备监测平台**：展示效果强，但容易被硬件稳定性拖累，也容易把“信号”误说成“事实”。
3. **社区照料闭环平台**：以社区工作流为主，老人 App、家属端、AI 和设备都作为事件来源或协作入口。

v1 选择第三种。理由是它最贴合智慧社区类别，也能在个人 10 周范围内形成完整、可演示、可验证的产品故事。硬件和云端 AI 都有替代路径，不成为核心流程的单点故障。

## 3. 产品定位与成功标准

### 3.1 一句话定位

帮助社区把独居老人的日常平安、异常求助、探访服务和后续回访连接成闭环。

### 3.2 目标用户

- 主要服务对象：75 岁及以上、基本自理的独居老人。
- 重点关注因素：慢性病、既往跌倒、行动能力下降、弱社会支持、近期异常。
- 不作为 v1 主要对象：重度失能、重度失智、需要连续医疗监护或机构照护的人群。

档案使用“常规关注、重点关注、高关注”三个社区照料关注等级，用于安排签到和探访频率。它由预置规则给出建议、社区人员确认，不是疾病严重程度或医疗诊断。档案关注等级、健康风险标签和单次照料事件等级是三种不同概念，不能相互覆盖。

### 3.3 参赛成功标准

- 从一键重置后的固定数据开始，在 5～7 分钟内稳定演示完整照料闭环。
- 设备重复上报、App 重试和后台任务重跑不会生成重复事件。
- 云端大模型不可用时，签到、求助、告警、接单和关单仍能运行。
- 所有关键状态变化都有责任人、时间、原因和审计记录。
- 界面使用正常产品文案，不展示“演示数据”等内部标记；模拟电话、120 和设备等外部动作仍须明确标注，避免制造真实运营的错觉。

### 3.4 明确不做

- 不提供 24 小时真实救援服务或救援时效承诺。
- 不接入真实 120、医院、短信、电话、支付或政府数据平台。
- 不做疾病诊断、在线问诊、处方、药物调整或生命体征连续监护。
- 不做精确定位、摄像监控、人脸识别或长期保存原始音频。
- 不做复杂排班、财务结算、服务商城和多社区 SaaS 计费。
- 不宣称参赛版本已经达到真实社区生产部署和合规验收标准。

## 4. 角色、权限和使用终端

| 角色 | 终端 | 主要能力 | 默认不可见内容 |
|---|---|---|---|
| 老人 | Flutter Android App | 签到、求助、查看提醒、AI 陪聊、管理授权与记忆 | 社区内部备注、他人档案 |
| 家属 | 同一 APK 的独立家属界面 | 查看已授权摘要、接收风险通知、查看照料进展 | 原始 AI 对话、未授权健康字段、社区内部备注、精确位置 |
| 社区工作人员 | Vue Web | 档案、告警、接单、探访、工单、回访、转介 | 非负责辖区数据、无业务需要的原始 AI 内容 |
| 服务人员/志愿者 | Vue Web 的受限角色 | 查看本人任务、最少必要联系信息、回填服务结果 | 完整健康档案、其他工单、家庭隐私 |
| 系统管理员 | Vue Web | 演示账号、规则、模板、种子数据、设备和运行检查 | 默认不读取日常 AI 原文，不代替社区处理事件 |

老人和家属虽然共用一个 APK，但登录后的导航、首页和信息范围完全分开。正常使用不提供角色下拉切换；受控设置入口允许切换预置账号，但不在界面展示内部演示标记。

## 5. v1 功能范围

### 5.1 必须完成

1. 账号登录、角色授权和辖区/任务数据范围。
2. 老人档案、紧急联系人、健康风险、服务需求和授权记录。
3. 平安签到、提醒、求助以及断网暂存。
4. 统一照料事件、分级规则、联系升级、负责人和状态机。
5. 社区探访任务、生活服务工单、结果回填和回访。
6. 家属端授权摘要和事件进展。
7. AI 陪伴问答、需求草稿、走访总结草稿、安全规则和固定内容降级。
8. ESP32 一键求助接入；硬件未就绪时由设备模拟器完整替代。
9. 通知、电话、上门和送医模拟中心。
10. 审计日志、运行检查和一键重置演示数据。

### 5.2 可在时间允许时增强

- 语音输入与文字转语音。
- 社区活动推荐和报名意向。
- 简单趋势图和照料成效摘要。
- 使用合成数据导出演示报告。

增强项不得挤占核心闭环、权限测试和失败降级的时间。

## 6. 核心业务模型

### 6.1 统一照料事件

所有风险和需求都先规范为“照料事件”，事件来源包括：

- 老人平安签到或漏签；
- 老人主动求助；
- 家属报告；
- 社区探访记录；
- ESP32 或设备模拟器信号；
- AI 对话中检测到的固定危险表达或待确认需求。

事件至少保存：来源、老人、等级、当前状态、责任人、触发时间、确认过程、关联任务、处理结果、回访结果和审计记录。事件等级与处理状态相互独立，紧急事件也必须经过接单和处理流程。

### 6.2 事件等级

| 等级 | 典型触发 | 系统动作 |
|---|---|---|
| 紧急 | 实体 SOS；明确表示跌倒后无法起身、胸痛、呼吸困难、自伤等 | 立即显示应急操作，建立紧急事件和模拟通知记录；120 动作为模拟 |
| 需要确认 | 漏签、设备异常、家属联系不上、含糊不适 | 提醒老人、生成电话确认任务；超时后按规则升级联系人 |
| 一般服务 | 助餐、保洁、陪伴、提醒、活动或普通走访需求 | 建立服务工单或探访任务，按计划处理 |

AI 只能产生“建议关注”或候选需求。紧急表达由确定性规则识别，不能由大模型自行判断是否危险。

### 6.3 状态机

```text
待确认 → 已接单 → 处理中 → 已解决 → 待回访 → 已关闭
   │          │
   ├→ 误报    └→ 无法确认 → 联系升级/重新派单
   └→ 无法确认 → 联系升级/重新派单
```

- `待确认`：事件已经创建，事实和负责人尚未完全确认。
- `已接单`：一个明确责任人已接受处理，系统记录接单时间。
- `处理中`：正在电话核实、上门或协调服务。
- `已解决`：本次直接问题有处理结果，但尚未完成后续确认。
- `待回访`：已经生成具体回访时间和责任人。
- `已关闭`：处理结果与回访结果完整，满足关单校验。
- `误报`：必须填写判断依据和处理人，是带原因的终态。
- `无法确认`：不是终态；必须触发联系升级、重新派单或人工决定下一步。

关闭事件必须满足：有负责人、有处理结果、需要回访时已有回访结果、没有未完成的强制任务。AI、设备和后台任务都无权自行关单。

### 6.4 去重和重试

- App 提交使用客户端请求 ID，设备使用事件 ID。
- 服务端对“来源 + 请求/事件 ID”建立唯一约束。
- 重复请求返回第一次处理结果，不重复创建事件或工单。
- 同一老人已有“安全/健康确认”类非终态事件，且新信号在该事件最近一次活动后的 30 分钟内到达时，系统把信号作为新证据附加到原事件；一般服务事件不自动合并安全信号。超出窗口则新建待确认事件。工作人员可以人工关联，但必须留下审计记录。
- 通知失败可以重试，但每次尝试写入独立通知记录。
- 逾期任务只升级责任，不篡改原事件事实。

## 7. 主演示故事

默认 20 份虚构档案中设置一位高关注老人作为主故事：

1. 系统完成一键重置，运行检查显示 App、Web、API、数据库、AI 和设备状态。
2. 老人未在约定时间签到，系统建立“需要确认”事件。
3. App 提醒和模拟电话均未确认，联系规则开始升级。
4. ESP32 或设备模拟器上报异常信号；系统把它合并到原事件，而不是新建重复事件。
5. 社区工作人员在 Web 接单，并启动模拟上门任务。
6. 走访回填“老人跌倒、意识清楚但无法自行起身”，确定性规则把事件升级为紧急。
7. 系统展示模拟联系家属和模拟拨打 120，明确标记没有真实外呼。
8. 工作人员记录模拟送医结果，建立防跌倒检查和次日回访。
9. 回访完成后关单，家属端只看到授权范围内的状态摘要。
10. 审计页回放整个时间线，说明每一步由谁、在何时、依据什么完成。

辅助演示故事包括正常签到、生活服务申请和 AI 陪聊识别“想找人说话”后生成陪伴服务草稿。

## 8. 页面与交互设计

### 8.1 老人端 Android

- **首页**：日期、天气、今日提醒、“我今天平安”、“我需要帮助”。比赛版天气使用种子数据或本地缓存，不增加外部天气接口依赖。
- **提醒**：服药、复诊、社区活动和探访安排；操作只有“已完成”和“稍后提醒”。
- **陪我聊聊**：文字和可选语音输入，支持朗读回复。
- **我的**：紧急联系人、数据授权、AI 记忆、字号和语音设置。

点击“我需要帮助”后再选择：紧急情况、身体不舒服、生活服务、想找人聊聊。这样既避免首页按钮过多，也降低误触紧急报警的概率。

### 8.2 家属端 Android

- **最近状态**：签到、提醒完成情况和社区最近一次确认时间。
- **事件**：只显示已授权事件摘要和处理进度。
- **照料记录**：探访、服务和回访摘要。
- **我的**：授权范围、通知设置和账号信息。

### 8.3 社区 Web

侧边导航固定为：工作台、老人档案、照料事件、探访任务、服务工单、设备信号、报告与审计、系统设置。

工作台只展示关键指标、待处理事项和跳转入口，不堆叠大面积装饰图表。告警列表优先展示等级、等待时长、老人、当前责任人和下一步动作。

### 8.4 适老化规则

- 大字号、高对比、大点击区域，一页只有一个主操作。
- 不依赖隐藏手势、横向滑动、长表单或颜色作为唯一提示。
- 关键结果同时提供文字、图标和可选语音反馈。
- 网络未发送成功时明确显示“尚未送达”，提供重试，不能假装成功。
- 危险操作需要第二次确认，但紧急页面必须始终保留醒目的求助出口。

## 9. AI 能力与安全边界

### 9.1 允许的能力

老人端：

- 回答一般生活、社区服务和常识性健康问题；
- 进行自然、尊重的陪伴对话；
- 把口语需求整理成待确认的服务申请草稿；
- 朗读较长内容。

社区端：

- 把走访记录整理成结构化摘要；
- 提取待办、服务需求和回访时间候选；
- 生成回访话术草稿。

所有 AI 内容都是草稿。老人或工作人员确认后，才可以写入正式档案、生成服务申请或对外展示。

AI 网关每次只发送当前任务所需、且调用者有权读取的最少上下文。模型不能直接调用业务操作；结构化草稿必须通过服务端数据结构和枚举校验后才展示。云端模型密钥由本机运行配置注入，不进入源码、种子数据、客户端或日志。

### 9.2 安全处理链

```text
用户输入
  → 输入侧固定危险规则
  → 紧急事件或普通 AI 请求
  → 云端大模型/固定内容降级
  → 输出侧医疗与安全规则
  → 标注为草稿
  → 人工确认
  → 写入正式业务记录
```

输入中明确出现跌倒后无法起身、严重胸痛、呼吸困难、意识异常或自伤表达时，固定规则直接展示应急指引并建立紧急事件，不等待大模型结论。

如果此时 Android 断网，App 先在本机显示应急指引和“事件尚未送达”，再把事件放入高优先级队列持续重试。参赛版的“联系 120”始终是模拟动作，不调用系统真实拨号能力。

AI 不得：

- 诊断疾病、判断“没有危险”、调整药物或给出剂量；
- 自动联系家属、120 或服务人员；
- 自行修改老人风险等级；
- 自行关闭照料事件；
- 隐瞒自己不可用、超时或使用了固定回复。

### 9.3 记忆与降级

- 默认只保留当前会话上下文。
- 原始文字消息仅用于当前会话，结束后不写入长期业务档案；系统只持久化经确认的服务草稿、摘要和记忆候选。
- 长期记忆先生成候选，由老人明确确认后保存。
- 老人可以查看和删除自己的 AI 记忆。
- 家属只看授权摘要，不看原始对话。
- 语音转文字完成后不保存原始音频。
- 云端模型不可用时，老人端使用固定关怀话术和 FAQ；社区端展示预生成的总结示例，并明确标记“AI 当前不可用”。

## 10. 设备设计

### 10.1 ESP32 一键按钮

- 老人长按约 2 秒触发，减少误触。
- LED 明确显示发送中、发送成功或发送失败。
- 上报内容只包含设备 ID、事件 ID、设备时间和按钮状态。
- 不采集音频、图像、精确位置或连续活动数据。
- 设备失败不能阻断 App 求助和社区处理流程。

ESP32 通过局域网 HTTP 接口上报 JSON，每台设备使用独立演示令牌。服务端以接收时间作为排序依据，设备时间只供诊断；令牌从本地配置注入，不写入源码、种子数据或日志。真实试点必须改用 TLS、正式设备身份和密钥轮换。

### 10.2 设备模拟器

Web 内置设备模拟器，可生成：按钮求助、长时间无用水、设备离线。模拟器与 ESP32 使用同一设备接入接口和幂等规则。

“长时间无用水”只能生成需要确认的信号，不能直接认定老人发生事故。比赛现场即使 ESP32 损坏，也能通过模拟器完成同一条业务链。

## 11. 技术架构

```text
老人/家属 Flutter App ─┐
社区 Vue Web 后台 ─────┼→ ASP.NET Core 模块化单体 → SQLite
ESP32/设备模拟器 ──────┘             │
                                     ├→ 规则与告警后台任务
                                     ├→ 云端大模型网关
                                     └→ 固定内容降级服务
```

### 11.1 部署方式

- 比赛笔记本运行 API、SQLite、Vue Web、后台任务和设备接入。
- Android 手机与 ESP32 通过同一局域网访问笔记本。
- 只有云端大模型需要互联网；核心照料闭环不依赖互联网。
- 提供本地启动脚本、一键运行检查和一键数据重置。

### 11.2 为什么采用模块化单体

个人 10 周项目不引入微服务、消息队列和 Kubernetes。模块化单体能够保留清晰边界，同时降低部署、调试和比赛现场运行风险。SQLite 便于携带和恢复；若进入真实试点，再评估 PostgreSQL、独立任务队列和高可用部署。

### 11.3 后端模块

| 模块 | 职责 | 主要依赖 |
|---|---|---|
| 身份与授权 | 本地账号、JWT、角色、辖区和任务范围 | 无业务模块依赖 |
| 档案与授权 | 老人档案、联系人、同意和字段级授权 | 身份与授权 |
| 签到与提醒 | 签到计划、提醒、完成记录、漏签检测 | 档案与授权 |
| 照料事件 | 事件、等级、状态机、负责人、联系升级 | 档案、签到、设备 |
| 探访与工单 | 走访、生活服务、回填、回访 | 照料事件 |
| AI 网关 | 会话、总结、固定规则、草稿和降级 | 档案授权、照料事件 |
| 设备接入 | 设备、信号、幂等、在线状态和模拟器 | 照料事件 |
| 通知模拟 | App 内模拟通知，以及模拟短信、电话、上门和送医记录 | 照料事件、探访与工单 |
| 报告与审计 | 时间线、操作审计、演示报告 | 只读聚合其他模块 |
| 演示运维 | 种子数据、重置、运行检查和诊断 | 全模块健康接口 |

模块之间通过应用服务接口和明确的数据契约协作，不能跨模块直接修改对方业务状态。后台定时任务使用 ASP.NET Core 托管服务即可，v1 不增加独立作业平台。

## 12. 核心数据模型

| 实体 | 关键内容 |
|---|---|
| UserAccount / RoleScope | 演示账号、角色、辖区或任务数据范围 |
| ElderProfile | 虚构姓名、年龄、居住情况、辖区、照料等级 |
| HealthRisk | 慢性病标签、跌倒风险、行动情况、来源和更新时间 |
| ServiceNeed | 助餐、保洁、陪伴、就医协助等需求；与健康风险分开 |
| EmergencyContact | 关系、模拟联系方式、联系顺序 |
| ConsentGrant | 授权人、被授权人、字段范围、有效期、状态 |
| Reminder / CheckIn | 计划时间、完成情况、客户端请求 ID |
| CareEvent | 来源、等级、状态、负责人、触发与处理结果 |
| ContactAttempt | 联系方式、模拟标记、尝试时间、结果 |
| VisitTask | 走访计划、执行人、记录、总结草稿和确认结果 |
| ServiceOrder | 服务类型、指派对象、最小必要信息、结果 |
| Device / DeviceSignal | 设备状态、事件 ID、信号类型和接收时间 |
| NotificationAttempt | App 内通知及外部动作模拟、尝试次数、结果和时间 |
| AiSession / AiDraft / MemoryCandidate | 不含长期原始对话的会话元数据，以及草稿、候选记忆、确认和删除状态 |
| AuditEntry | 操作者、动作、对象、前后状态、时间和原因 |

所有业务实体使用稳定 ID、创建时间和更新时间。正式业务变更通过状态操作完成，不能以直接覆盖整行数据的方式绕过审计。

## 13. 数据、授权与隐私

### 13.1 数据原则

- 默认种子为 20 份、可配置在 15～25 份范围内的完全合成档案。
- 所有页面使用正常产品文案；电话、120、通知和设备模拟等非真实动作必须持续显示明确的“模拟”或“不真实拨号”提示。
- 使用固定随机种子，保证重置后主故事和统计结果一致。
- 重置需要确认，目标在 1 分钟内恢复初始状态。
- 日志不记录密码、访问令牌、完整 AI 原文、原始音频或不必要的健康字段。

### 13.2 授权规则

- 老人查看自己的数据、授权和 AI 记忆。
- 家属只读取老人明确授予的字段和摘要。
- 社区人员只处理负责辖区数据。
- 服务人员只读取完成当前任务所需的最少字段。
- 管理员管理账号和规则，默认不读取原始 AI 对话。
- 紧急破窗访问必须填写原因、限定时效并写入审计。

撤回家属授权后，立即阻止新的读取；历史审计仍保留，但家属不再通过业务界面查看后续数据。参赛版采用独立网络和合成数据。真实试点前必须另行完成数据保护影响评估、传输与数据库加密、密钥管理、备份恢复、安全测试和线下授权流程。

## 14. 失败处理与可诊断性

| 故障 | 用户看到什么 | 系统如何处理 |
|---|---|---|
| Android 断网 | “尚未送达”，可重试 | 本地排队、恢复后按请求 ID 幂等提交 |
| 云端 AI 超时/断网 | “AI 当前不可用” | 固定话术、FAQ 或预生成示例，不影响核心流程 |
| ESP32 掉线 | 设备离线和最后在线时间 | 本地重试；社区仍可用 App 和模拟器 |
| 设备重复上报 | 同一事件只显示一次 | 服务端唯一键返回原结果 |
| 后台任务失败 | 运行检查显示失败模块 | 记录任务日志和重试次数，不静默吞错 |
| 通知模拟失败 | 事件页显示未送达 | 允许重试，保留每次尝试记录 |
| SQLite 忙或写入失败 | 操作未完成的明确提示 | 短退避重试；事务失败不返回成功 |

启动检查分别验证 API、数据库、后台任务、AI 配置、设备接口和局域网地址，不能只给出笼统的“系统正常”。

## 15. 测试方案

### 15.1 自动化测试

- **后端单元测试**：分级规则、状态机、关单条件、授权判断、幂等和升级计时。
- **后端集成测试**：数据库事务、身份权限、事件到工单的完整 API 流程、重置一致性。
- **Flutter 测试**：老人主流程、家属权限、离线排队、错误提示和关键适老化组件。
- **Vue 组件与端到端测试**：告警接单、探访回填、工单、回访、审计和受限服务人员视图。
- **AI 契约与安全测试**：危险表达、禁止诊断、禁止改药、超时、坏格式和固定降级。
- **设备测试**：长按、误触、重复事件、离线、重连和模拟器契约一致性。

### 15.2 全链路场景

至少验证：正常签到、漏签升级、实体 SOS、设备异常合并、生活服务申请、AI 陪聊需求草稿、AI 危险表达、家属撤回授权和云端 AI 断网。

### 15.3 验收清单

1. 种子数据包含 15～25 份档案，默认 20 份，覆盖至少三个照料关注等级。
2. 一键重置后主故事可重复，目标 1 分钟内恢复。
3. 主故事可在 5～7 分钟内完成。
4. 待确认事件有且仅有一个责任队列；接单后至终态有且仅有一位当前负责人，所有变化可审计。
5. App 重试和设备重传只产生一个业务事件。
6. 云端 AI 不可用时核心流程仍可完成。
7. 系统不发送真实外部消息，不使用真实个人资料。
8. 家属越权、服务人员越权和撤回授权测试通过。
9. 运行检查能逐项报告依赖状态和修复提示。
10. 如果能招募到 5 名以上 60 岁及以上志愿者，仅用合成数据完成基础可用性观察并如实记录；该观察不能替代 75 岁以上目标人群验证。如果不能，则明确写明“尚无真实老人可用性证据”。

## 18. 风险与真实落地前置条件

| 风险 | v1 控制办法 | 真实试点仍需完成 |
|---|---|---|
| 硬件现场不稳定 | 同契约设备模拟器 | 设备选型、网络覆盖、耐久与失效测试 |
| 大模型断网或输出不当 | 固定规则、草稿确认、固定内容降级 | 模型评估、内容治理、供应商与数据协议 |
| 告警误报或漏报 | 信号只进入待确认、去重、人工决策 | 真实数据验证、阈值校准和责任制度 |
| 社区缺少线下资源 | 只演示派单与处理记录 | 服务商、人员、排班、SLA 和应急预案 |
| 适老化未经真实验证 | 遵循基础规范并如实披露 | 老人参与式研究和持续可用性测试 |
| 隐私与安全 | 合成数据、最小权限、审计 | 合规评估、加密、密钥、备份、渗透测试 |

答辩时可以证明的是“软件闭环能够稳定演示并在失败时降级”，不能证明真实事故发现率、真实救援时效、真实老人满意度或生产级安全合规。
