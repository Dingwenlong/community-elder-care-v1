# 参赛演示讲稿

目标时长 6 分钟。全程使用 20 份固定虚构档案。电话、短信、120 和设备动作都要口头说明为模拟，不要跳过页面上的“演示数据”标识。

## 上台前

在同一个 PowerShell 进程中完成环境载入、启动和重置：

```powershell
. .\scripts\dev-env.ps1
.\scripts\start-demo.ps1
.\scripts\reset-demo.ps1
```

打开脚本输出的 Web 地址。老人端使用已装好的演示 APK。若现场没有 ESP32，直接使用管理员的“设备信号”模拟器。

## 0:00 至 0:45，问题和边界

先说一句：社区最难的不是收到一次报警，而是把平安确认、异常核实、上门探访、家属知情和后续回访接成一条有人负责的记录。

指出登录页上的两项边界：20 份档案全是虚构数据；外部电话和设备动作全是模拟。系统不诊断疾病，也不会真的拨打 120。

## 0:45 至 1:25，老人漏签

进入社区工作台。重置后，主老人“演示·李安康”的平安确认已经超时。后台任务只生成一条待确认事件，多次运行也不会重复建单。

打开照料事件，记住事件编号。后面的设备信号、探访和联系动作都回到这个编号。

## 1:25 至 2:05，设备补充证据

硬件可用时，长按 ESP32 SOS 按钮。没有硬件时，在管理员“设备信号”页点击“模拟长时间无用水”。

回到事件详情，说明设备信号不是直接结案的依据。它作为新证据合并到刚才的事件，社区仍要人工受理。

## 2:05 至 3:15，受理和探访

用 `community.demo` 登录，受理事件。进入探访任务，开始探访并提交三项内容：

- 内部原始记录：只给社区人员看。
- 对外确认摘要：可以进入家属授权范围。
- 探访结果：用于后续处置和审计。

提交后回到事件详情。时间线已经有受理、开始处理和探访完成记录，原始探访笔记不会出现在审计接口。

## 3:15 至 4:15，模拟联系和安全升级

依次点击“模拟电话”和“模拟急救转运”。页面必须显示“模拟送达”，不能说成已经联系家属或已经呼叫 120。

如果要展示失败分支，先运行故障演练中的通知失败用例。失败记录保留在审计中，操作员换一个请求编号重试，旧失败不会被覆盖。

## 4:15 至 5:15，解决、随访和结案

把事件转为已解决，填写处理依据和结果。随后安排一次随访并记录“状态稳定”。

在随访完成前尝试结案，服务器会拒绝。随访完成后再结案。最终状态为“已结案”，事件编号仍是开场时的那一个。

## 5:15 至 6:00，家属视图和审计

切到家属端。家属只看到老人授权的最近状态、事件摘要和探访摘要，看不到内部笔记、完整健康风险或 AI 原始输入。撤回授权后，下一次读取立即被拒绝。

最后用管理员打开“报告与审计”和“系统设置”。展示合成统计、每项就绪状态、事件时间线和重置入口。收尾只说已经证明的内容：这是一套可重置、可审计的参赛演示系统，实地照护仍由社区人员完成。

## 现场备路

ESP32 断线时用 Web 设备模拟器；云端 AI 不可用时使用本地危险词规则和固定提示；手机掉线时求助留在本地队列，网络恢复后用同一个请求编号重发。API 无法恢复时播放忽略目录中的自动化主故事录像，并保留所有“模拟”“演示数据”标签。
